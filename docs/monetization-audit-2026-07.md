## 1. クイズ記事間のSPA遷移で記事内広告がリフレッシュされない 【最重要】

**該当**: `src/lib/components/AdSense.svelte:23-55`、`src/lib/components/QuizDetailPage.svelte:203,238,293`、`src/routes/category/[categorySlug]/[quizSlug]/+page.svelte`

**現状の挙動**:

- クイズ詳細（canonical: `/category/[categorySlug]/[quizSlug]`）から関連記事・InlineCta 経由で**別のクイズ詳細**へ遷移すると、SvelteKit は同一ルートのためページコンポーネントを**再利用**する。`QuizDetailPage` 内の `AdSense` インスタンスも破棄されない。
- `AdSense.svelte` はパス変更を検知して `adsbygoogle.push({})` を再実行するが、**同じ `<ins>` 要素**に対して push するため、AdSense 側は「already have ads in them」で例外を投げる（`try/catch` で握り潰し）。その後 `syncHeight()` が既存 iframe の高さを検出して**前ページの広告をそのまま再表示**する。
- 結果: 関連記事→次のクイズという**回遊の主動線で発生する2ページ目以降のPVでは、記事内3枠（タイトル下・画像下・関連記事上）の新規インプレッションがほぼゼロ**になる。

**改善案（レポートのみ・参考）**: パス変更時に `<ins>` 要素を DOM ごと作り直す（`{#key $page.url.pathname}` で AdSense コンポーネント自体を再生成するのが最小変更）。ページ遷移に伴う広告再描画は AdSense ポリシー上も正当。

- **期待効果**: 回遊による2PV目以降で記事内広告の在庫が復活。回遊率次第だが、**記事内枠インプレッションの +20〜40% 回復**が見込める最大の伸びしろ。
- **工数**: S〜M（実装は小、実機での再描画・二重push・CLS確認に時間を割く）。
- **リスク**: 低〜中。`{#key}` 再生成時に一瞬の空白（既存の「トルツメ」ネガティブマージンで吸収可能）。自動リフレッシュ（無操作更新）と誤認されない設計（ユーザー遷移起点のみ）を守ること。

## 2. 内部リンクがほぼ全て旧URL `/quiz/[slug]`（308リダイレクト経由）

**該当**: `src/lib/components/ArticleCard.svelte:59`、`InlineCta.svelte:46`、`QuizDetailPage.svelte:56,184`、`answer/+page.svelte:158`

**現状**: canonical URL は `/category/[cat]/[slug]`（sitemap もこちらを掲載）だが、記事カード・関連記事・InlineCta・「さらにもう一問」・「問題ページに戻る」など**サイト内リンクは全て `/quiz/[slug]`** を指し、サーバー側で 308 リダイレクトされている。

- ユーザー側: 回遊クリックごとにリダイレクト1往復分の遅延（クライアントナビゲーションでもデータ取得→308→再取得）。
- SEO側: **canonical ページへ直接張られた内部リンクがほぼ存在しない**状態。リンクエクイティと内部リンクシグナルがリダイレクト越しになり、クロールも二度手間。

**改善案**: プレビューデータに `category.slug` が既に含まれているため、`quizHref(quiz)` ヘルパーで `/category/[cat]/[slug]` を直接生成（カテゴリ欠損時のみ `/quiz/` フォールバック）。解答への導線 `answerPath` も同様。

- **期待効果**: 回遊1クリックあたり約100〜300msの短縮、クロール効率とcanonicalページへのリンク評価集約 → 検索・Discover流入の底上げ。
- **工数**: M（リンク生成箇所が分散。テスト `tests/quiz-pages.test.mjs` への影響確認込み）。
- **リスク**: 低。308 フォールバックが残るため取りこぼしても現状と同じ挙動。

## 3. サイドレール広告がセッション中1回しか描画されない

**該当**: `src/routes/+layout.svelte:22-33,136-140`

**現状**: サイドレール（160×600 ×2）は `onMount` 時に1回だけ `<ins>` を生成して push。レイアウトはSPA中破棄されないため、**何ページ回遊しても同じ広告が表示され続け、インプレッションは初回の1回分のみ**。また `window.innerWidth >= 1540` 判定も初回のみ（リサイズ・回転非対応）。押し込みも即時実行で遅延読込なし。

- **期待効果**: ページ遷移ごとに再描画すれば、ワイドPCユーザーのPV数ぶんサイドレール在庫が増加（現状はセッションあたり2imp固定）。
- **工数**: S（`afterNavigate` で `<ins>` を作り直す）。
- **リスク**: 低。#1と同じく「ユーザー遷移起点の再描画」に限定すること。

## 4. タブレット〜ノートPC幅（768〜1539px）の一覧ページ広告が実質1枠

**該当**: `src/lib/components/ArticleFeed.svelte:70-74`（インフィードは `min-width:768px` で `display:none`）、`+layout.svelte:542`（サイドレールは `min-width:1540px` 限定）

**現状**: TOP・カテゴリ一覧の「記事3枚ごと」インフィード4枠はSP専用。768〜1539px（iPad・大半のノートPC）では一覧上部の1枠のみ。**脳トレ系はシニアのタブレット比率が高い**傾向があり、GA4のデバイス内訳次第では大きな空白地帯。

- **期待効果**: 対象幅のセッション比率×一覧PVぶんのインフィード在庫が新規に発生。一覧ページRPMの押し上げ。
- **工数**: S〜M（CSS解除＋グリッド内での見え方調整。PC用は `data-ad-format` の見直しやFluid枠新設が望ましい）。
- **リスク**: 中。一覧の広告密度が上がるためUX・ポリシー(コンテンツ比率)を確認しつつ、まず1〜2枠から段階導入を推奨。

## 5. `noindex,nofollow` の適用範囲が広すぎる

**該当**: `src/routes/+layout.svelte:46,95-96`、`src/lib/components/SEO.svelte:97`

**現状**:

1. クエリ付きURL（`/?page=2`、`/category/x?page=2`、UTM付き流入URL等）が一律 `noindex,nofollow`。
2. 解答ページも `noindex,nofollow`。
3. `nofollow` のため、**ページネーション経由で13件目以降の旧記事へ渡る内部リンク経路がクローラーから完全に遮断**され、旧記事の発見が sitemap 頼みになる。解答ページ→関連記事・「さらにもう一問」へのリンク評価も消失。

**改善案**: 少なくとも `noindex,follow` に変更。ページネーションは canonical 自己参照つきで index 許可も検討（アーカイブの深いページを資産化）。

- **期待効果**: ロングテール記事のクロール頻度・インデックス維持が改善し、アーカイブからの検索流入（＝広告収益の複利部分）を守る。
- **工数**: S（`SEO.svelte` の1行＋レイアウトの条件整理）。
- **リスク**: 低。UTM付きURLの noindex 自体は維持してよい（canonicalは既にクエリなしを指している）。

## 6. 「戻る」操作を含む全遷移で強制スクロールトップ（回遊阻害）

**該当**: `src/routes/+layout.svelte:60-69,116-134`（`history.scrollRestoration='manual'`＋`afterNavigate` で常にトップへ）

**現状**: vignette 広告のスクロール位置バグ対策として、**ブラウザバックを含む全ナビゲーションでページ先頭へ強制スクロール**している。一覧を深くスクロール→記事閲覧→戻る、でリスト先頭に戻されるため、2本目以降の記事クリック（＝広告インプレッションの源泉）を自ら削っている。

**改善案**: 強制トップ復帰を「vignette が開いていた遷移」に限定し、通常の popstate（戻る/進む）はブラウザ標準のスクロール復元に任せる。

- **期待効果**: 一覧→記事→一覧の往復回遊が滑らかになり、セッションあたりPV増（体感の効く UX 改善）。
- **工数**: M（vignette バグの再発確認が必要なため実機検証が重い）。
- **リスク**: 中。vignette 由来のスクロール不具合が再発しないよう条件分岐を慎重に。

## 7. タイトル下「固定レクタングル」枠の高さ未予約による CLS

**該当**: `src/lib/components/AdSense.svelte:117-152`、`QuizDetailPage.svelte:441-445`（トルツメ用ネガティブマージン）

**現状**: 全広告枠が「高さ0で開始→配信確定後に出現」する設計。未配信時の余白は消えるが、**配信された瞬間に本文全体が押し下がる**。特にタイトル直下の枠（コメントに「必須配信」とあり fill 率がほぼ100%）はファーストビュー内のため、実ユーザーの CLS を継続的に悪化させる。CWV は検索・Discover の可視性、ひいては誤クリックでなく安定した視認クリックにも影響。

**改善案**: 「必須配信」の固定レクタングル枠のみ `min-height`（配信サイズ固定なら実測値、レスポンシブなら 250〜280px）を予約。前回監査で保留になった「未配信時の空白」問題は、fill 保証のあるこの枠に限定すれば回避できる。

- **期待効果**: 記事ページの CLS 改善 → CWV 起因のランキング/Discover 抑制リスクの解消、ビューアビリティ安定。
- **工数**: S〜M。
- **リスク**: 中。未配信時に空白が残るケースの監視が必要（この枠に限定して導入し計測で判断）。

## 8. 本番でトークン設定時に Sanity CDN が無効化される

**該当**: `src/lib/sanity.server.js:83-89`（`useCdn: !hasToken`）

**現状**: `SANITY_READ_TOKEN` 等5種のうち**どれか1つでも Vercel に設定されていると全 GROQ クエリが CDN を経由せず**ライブAPI直撃になる。ホーム/カテゴリは CDN キャッシュ（s-maxage=1800）で緩和されるが、キャッシュミス時の TTFB と Sanity API 課金が悪化する。

**改善案**: `useCdn` はプレビュー(previewDrafts)有効時のみ false にする明示制御へ。

- **期待効果**: キャッシュミス時の TTFB 短縮、Sanity API コスト削減。
- **工数**: S。
- **リスク**: 低（ISR/webhook 再検証があるため鮮度への影響は軽微）。

## 9. The Moneytizer CMP を全ページで読み込むが配信タグが存在しない

**該当**: `src/app.html:27-186`（inmobi choice.js＋TCF/USPスタブ）、`static/ads.txt:2`（`MANAGERDOMAIN=themoneytizer.com`＋大量のリセラー行）

**現状**: コード内に The Moneytizer の広告タグは存在せず（検索済み）、AdSense のみが配信実装。にもかかわらず全ページの `<head>` 先頭で同社の CMP スクリプト（+6秒間隔のUSPポーリング）を実行しており、初期表示のJSコストだけ払っている。前回監査でも「実態確認」が未対応のまま。

**改善案**: 契約状況を確認のうえ、(a) 配信再開するならタグを実装して在庫を増やす、(b) 終了しているなら CMP と ads.txt の Moneytizer 系行を撤去して軽量化、のどちらかに倒す。

- **期待効果**: (a)ならヘッダービディング系の追加収益、(b)なら全ページの初期JS削減と ads.txt の健全化。
- **工数**: S（技術作業自体は小。ビジネス確認が律速）。
- **リスク**: 中。**契約確認前に消すのは厳禁**（配信実績があれば収益断絶）。

## 11. 記事ページでグローバルナビ・パンくずを非表示

## 13. デフォルトOG画像がSVG＋`logo.png` が約1MB

**該当**: `src/lib/config/site.js:9`（`defaultOgImage: 'https://noutorebiyori.com/logo.svg'`）、`static/logo.png`（約1MB、JSON-LD publisher.logo と OGP フォールバックに使用）

**現状**: 記事以外のページ（TOP等で画像解決に失敗した場合）の OGP が SVG になる。X/Facebook/LINE など主要スクレイパーは SVG を描画しないため、**共有カードが画像なしになりCTRを落とす**。また 1MB の logo.png をクローラー・共有プレビューが都度取得。

**改善案**: 1200×630 の圧縮PNG/WebP をデフォルトOGに用意、logo.png は 100KB 以下へ圧縮（前回監査でツール不在により見送りのまま）。

- **期待効果**: SNS・Discover 経由の流入CTR改善（小幅だが恒常的）。
- **工数**: S。
- **リスク**: 低。

## 14. ナビのカテゴリがハードコード混在＋レイアウト load が毎遷移実行

**該当**: `src/routes/+layout.server.js:4-33`（`MENU_ITEMS` ホワイトリスト＋`url` 返却）、`+layout.svelte:283-311`（4カテゴリをハードコード）

**現状**: Sanity で新カテゴリを公開してもナビには自動反映されず（`MENU_ITEMS` に無いものは落ちる）、別途4カテゴリがテンプレートに直書き。新設カテゴリの立ち上がり期に内部リンクが張られず回遊・SEOの初速を損ねる。また `url` を返しているためレイアウト load が全遷移で再実行され、ナビゲーションごとに余計なデータリクエストが1本走る。

- **期待効果**: カテゴリ追加の運用コスト削減と新カテゴリの立ち上がり改善、遷移1本あたりのリクエスト削減。
- **工数**: S。
- **リスク**: 低（表示順の制御をSanity側フィールドに持たせる設計判断のみ）。

## 15. 問題/解答ページのURL階層不整合・FAQスキーマの重複

**該当**: `src/routes/quiz/[...slug]/answer/`（解答は `/quiz/[slug]/answer` のみ）、`quiz/[...slug]/+page.server.js:83-84` と `answer/+page.server.js:87-99`（問題・解答の両方に同内容の FAQPage）

**現状**:

- 問題ページの canonical は `/category/...` 階層へ移行済みだが、解答ページは旧 `/quiz/...` 階層のまま。解答→「問題ページに戻る」も `/quiz/` 経由（#2のリダイレクト問題と連動）。トピック権威をURL階層で示す方針なら解答も同階層に揃えるのが一貫的。

- **期待効果**: URL構造の一貫性によるクロール効率化、不要スキーマの削減（実利は小）。

- **リスク**: 低〜中（URL移設はリダイレクトミス時の影響が大きいので #2 対応後に検討）。

## 良好で維持すべき点（変更不要）

- **問題/解答の2ページ構成**: 1コンテンツで2PV＋計7枠の在庫を生む収益設計の核。解答ページの noindex 化も重複・低品質評価回避として妥当。
- **ISR（`expiration:false`）＋webhook再検証＋CDNキャッシュ**: 記事ページの配信は高速・低コストで模範的。
- **AdSense の遅延初期化（IntersectionObserver rootMargin 400px）と unfilled 時のトルツメ**: ビューアビリティとUXの両立。
- **画像最適化**: Sanity 変換（AVIF/WebP srcset、width/height 付与、LCP画像の `fetchpriority=high`）、システムフォントのみで Web フォント負債なし。
- **SmartNews/TRILL/merkystyle への配信フィード**: 収益源の分散として機能。
- **Consent Mode v2・ads.txt（自社 pub ID DIRECT 登録済み）・www→apex 301** などの基盤整備。
